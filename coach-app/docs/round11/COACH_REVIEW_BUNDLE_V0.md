# Round 11 — One-call, evidence-verified review bundle

## Why this exists

The previous real-replay browser workflow sent a decoded replay to
`/api/decision-cases` and then posted the same large replay again for each
`/api/coach/lesson`. That approach incurs repeated full-payload serialization,
bandwidth, and redundant episode construction. It also binds the UI to event
candidate extraction rules that were not designed to prove tactical mistakes.

This implementation gives the frontend one deterministic, bounded backend
call that selects source-audited moments and prepares their actual lessons.

## Architecture decisions

We evaluated three approaches:

1. **Client chain of candidates + per-lesson requests (current legacy).**
   Easy to inspect but retransmits a full decoded replay repeatedly and requires
   multiple roundtrips; the browser has to stitch partial success and failure.
2. **Server-side retained sessions with an opaque replay ID.** Would make
   repeated followups cheaper but introduces sensitive replay retention,
   lifecycle, limits/evictions, concurrency and restart consistency. Not adopted
   for a private, local-first prototype without those storage/security controls.
3. **One-call stateless bundle (implemented).** Sends the decoded replay
   *once*, uses the existing Stage 1 candidate and lesson builders,
   prepares a bounded number of selected lesson previews, and returns both
   complete candidates and explicit omissions. No replay cache or background
   service. Slightly more CPU per initial request but low conceptual and
   privacy overhead; the other existing endpoints remain fully supported.
4. **Precompute all lessons for an entire match.** Rejected: unnecessarily
   expensive, large responses, and most uncalibrated leads will never be viewed.

Choice #3 is designed to make real-replay UI integration dependable, not to
increase the perceived accuracy of coaching.

## API

`POST /api/coach/review-bundle`

Request:

~~~json
{
  "replay": {"players": [], "frames": [], "events": []},
  "player_id": "selected-player-id",
  "max_candidates": 8,
  "preview_count": 3,
  "experimental_tactical_v1": false
}
~~~

The `replay` above is a **shape illustration**, not a valid replay by itself.
A real request needs the original decoded 2v2 replay from the local upload API.

- Exactly four players, two blue/two orange, known focal player.
- Body must be JSON, at most 24 MiB; up to 30,000 frames and 30,000 events.
- `max_candidates` = 1–12; `preview_count` = 0–4 (default 3). If fewer
  candidates exist, only that number is previewed.
- Optional `horizon_s` selects from the frame prefix only (supports temporal
  invariance testing; must be within the replay).
- V0 tactical menu is the default; `experimental_tactical_v1:true` adds
  a separate **unverified** comparison only in local deterministic mode.
  There is no `model` parameter and the endpoint never calls a model.
- Same-origin protections from the local FastAPI app still apply.
- Does not persist replay bytes or an opaque replay cache.

Response contract `CoachReviewBundleV0`:

- `schema`, `stage:"predecision"`, `mode:"local_deterministic"`.
- `status:"ok"|"partial"|"no_supported_candidates"`.
- `discovery`: unchanged full `EpisodeCandidatesV0` object.
- `candidate_count`: total source-audited candidate count.
- `preview_count`, `preview_attempts`: actual ready and attempted lessons.
- `previews[]`: each is `{candidate_id, primary_t0, node_semantics,
  selection_reason:{signal, source_refs, rule}, lesson:CoachLessonV0}`.
- `unavailable_previews[]`: `{candidate_id, reason_code}` when a lesson
  cannot safely be constructed, with no internal exception/error text.
- `selection`: explicitly states observational (not tactical) priority,
  unverified node semantics and no model use.
- `privacy`: indicates no raw frames/names in the response or server replay
  retention. The original replay is still transmitted *to the same local server*
  as part of the initial request.

The backend takes highest-salience **observational** changes for previews,
then returns them in chronological order. This is NOT a ranking of mistakes or
a claim about which situation best explains winning/losing a match.

Every `lesson` is generated by the existing `build_episode_evidence` →
`build_stage1_episode_packet` → `build_lesson_from_episode` process. The
endpoint separately checks output type, decision time, Stage 1, unchanged V0
default and deterministic undetermined grade. V1 optional comparison goes
through the strict independent verifier on PR #38.

### Browser handoff to Antigravity

1. After a **real, confirmed 2v2 replay** upload and player selection, check
   `GET /api/coach/capabilities` for `single_request_review_bundle`.
2. If present, `POST /api/coach/review-bundle` with the replay and selected
   player. Show a cancellable loading state and ignore responses for superseded
   replay/player selections.
3. Render `discovery.candidates` as **review leads**. Clicking a candidate
   seeks its `primary_t0` in the 2D + **high-fidelity** synced views.
   Basic geometric 3D is retired and must not reappear.
4. Match `candidate_id` to `previews[].candidate_id`. Display its actual
   `CoachLessonV0` if present; otherwise request the selected candidate
   separately via `POST /api/coach/lesson` with its original time fields.
   Never substitute fixture claims.
5. Respect `node_semantics`: N1 is a comparison observation, **not** an
   identified causal earlier error; N2 is a changed-state endpoint, not a
   validated tactical decision. Do not label links a chain of mistakes.
6. Evidence chips still resolve through `POST /api/coach/evidence`; followup
   text through `POST /api/coach/followup` is **local evidence navigation**,
   not free-form AI coaching. These existing endpoints currently require
   replay input again; this V0 bundle reduces initial requests but does not
   solve every later retransmission.
7. If `status=no_supported_candidates` or a preview is unavailable, show
   the honest state and a **manual timeline exploration** affordance. Keep
   simulated fixtures in an explicitly selected demonstration mode.
8. Do **not** enable V1 unless the user explicitly opts in to an experiment.
   Show its `expert_validated:false` caveat. Never surface V1 as a final
   coaching grade or send its analysis to a paid model.

## Acceptance and limitations

- All code is side-effect-free and stateless. No model calls, native game
  commands, replay storage or uploads to third-party providers.
- Error handling distinguishes full-request invalidity (422) from individual
  lesson-preview omissions (200 + `unavailable_previews`).
- Unit and API tests cover consistency with direct `/api/coach/lesson`,
  source-audited candidate matching, bounded preview work, V1 separation,
  future-data rewrites after a cutoff, abstention, malformed inputs, privacy
  labeling, and cross-origin refusal.
- **Not yet established:** real 2v2 browser performance on multiple
  replay sizes, high-rank coaching merit, expert verdicts, desktop viewing
  fidelity, native camera-toggle recovery, and overall frontend handoff.
- Existing parser and API size limits still constrain large games. Heavy
  requests must be measured on user-approved replay samples before release.
- The current bundle's two-node episodes are source-observation comparisons,
  not automatically discovered chains of causal decisions.

The test suite and CI status for this branch, not this document, are the
authority for exact execution results.
